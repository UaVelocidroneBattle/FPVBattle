# Frontend Conventions

React 18 + TypeScript dashboard in `frontend/`: Vite, Zustand, TailwindCSS, Radix UI and Nivo charts.

## Approach

- Teach React and Zustand best practices while implementing: explain *why* a pattern was chosen, and contrast correct and incorrect patterns where it helps.
- Check current documentation (context7 when available) for React, Zustand and TypeScript patterns before writing state management or hook code.
- Write idiomatic code. Components render, stores manage state, and hooks coordinate.
- No `setTimeout` hacks, no manual state synchronization, and no `useRef` flags to coordinate effects.

## Components

Declare components as plain functions with typed props. Never use `React.FC`: it adds an implicit `children` prop and weakens inference. A few legacy files still use it; convert them when you touch them.

```tsx
interface ComponentProps {
    name: string;
    className?: string;
}

function MyComponent({ name, className = "" }: ComponentProps) {
    return <div className={className}>{name}</div>;
}
```

### Where files go

| Kind | Location |
| --- | --- |
| Generic UI (buttons, dialogs, popovers, segmented controls) | `src/components/ui/` |
| Reusable business components (leaderboards, track names, notifications) | `src/components/` |
| Page-specific components and hooks | next to the page in `src/pages/<feature>/` |
| Hooks used across pages | `src/hooks/` |
| Zustand stores | `src/store/` |

- Move a component or hook to a shared location once a second consumer needs it, or when it has no page-specific logic. Update all imports when you move it.
- Name page files `[Feature]Page.tsx` and layouts `[Name]Layout.tsx`. Never use `index.tsx` for a page.

### Windows file casing

The primary dev environment is Windows, which has a case-insensitive filesystem.
- Never change the case of a file already committed to Git. Rename the component and its exports, not the file path.
- Use the correct casing from the start for new files. TypeScript is case sensitive even on Windows.

## API client

The client is generated by `@hey-api/openapi-ts` from `shared/api/FpvBattle.Web.json` into `src/api/client/`. Never edit the generated files.

- Run `npm run gen` after backend API changes. `npm run gen:full` also rebuilds the backend to refresh the spec first.
- Call the generated SDK functions and import their types from `@/api/client`:

```ts
import { getApiTeamsDetails } from "@/api/client";
import type { TeamDetailsModel } from "@/api/client";

const response = await getApiTeamsDetails({ query: { teamId } });
if (response.data) set({ details: response.data, detailsState: "Loaded" });
else set({ detailsState: response.response.status === 404 ? "Idle" : "Error" });
```

- A failed request comes back as `response.error` with a non-OK `response.response`. A network failure throws. Handle both.
- Track request status with `LoadingStates` (`"Idle" | "Loading" | "Loaded" | "Error"` from `@/lib/loadingStates`), not with separate boolean flags.

## Zustand

### Store shape

Separate the state and actions interfaces:

```ts
interface TeamsState {
    details: TeamDetailsModel | null;
    detailsState: LoadingStates;
}

interface TeamsActions {
    selectTeam: (teamId: number) => Promise<void>;
}

type TeamsStore = TeamsState & TeamsActions;

export const useTeamsStore = create<TeamsStore>()((set, get) => ({ /* ... */ }));
```

- Guard against stale responses: when a newer request has started, ignore the older answer (compare with `get()` before `set`).
- Skip a fetch already in progress instead of firing a duplicate request.

### Rules that prevent infinite loops

1. **`useShallow` only for objects and arrays**, never for a primitive selector:
   ```ts
   const { load, search } = useTeamsStore(useShallow((s) => ({ load: s.load, search: s.search })));
   const detailsState = useTeamsStore((s) => s.detailsState); // primitive: no useShallow
   ```
2. **Call actions inside effects through `getState()`**, so the dependency list holds only the real inputs:
   ```ts
   useEffect(() => {
       useTeamsStore.getState().selectTeam(teamId);
   }, [teamId]);
   ```
3. **Keep selectors simple.** A selector that builds a new array or object on every call re-renders forever. Select the raw data and derive with `useMemo`:
   ```ts
   const items = useStore((s) => s.items);
   const processed = useMemo(() => items.map(toRow), [items]);
   ```

## URL ↔ store sync

When a page's state is shareable through the URL (see `pages/statistics/performance/useUrlPilotSync.ts`), use the store-first pattern:

1. The store is the source of truth.
2. URL parameters, when present, override the store (sharing and bookmarks).
3. Store changes update the URL, but don't clear an existing URL on the first render.
4. Store changes trigger data fetching.
5. Without URL parameters, the store stays as it is, so state persists across navigation.

Never write two independent effects that sync the URL and the store into each other.
